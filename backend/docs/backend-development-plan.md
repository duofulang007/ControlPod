# APEX 总控台后端完善计划

## 这份计划解决什么

目前后端已经能真实保存项目、任务、项目记录、应用、项目文件、执行模块绑定和运行记录；也能通过 `ModuleRunner` 启动 APEX 模块或打开网页模块。下一步不应再堆更多页面接口，而是让“一个项目由多个步骤可靠地运行”成为稳定能力，并把目前集中在 `app/main.py` 的职责拆清楚。

这轮的最终目标是：用户点击“运行项目”后，后端能明确告诉页面 **正在执行哪一步、成功了哪些步骤、在哪里失败、是否能关闭或重启**；服务重启后也不会把不确定的状态说成“仍在运行”。

不在本轮范围内：版本/快照/清理策略数据、云端同步、消息队列、React/Vue 或新的前端构建系统。

## 先理解现状

| 已有能力 | 目前的位置 | 局限 |
| --- | --- | --- |
| HTTP 接口、参数校验、静态页面 | `app/main.py` | 路由、业务规则和 SQL 混在一个文件里，后续改动容易互相影响。 |
| SQLite 与安全迁移 | `app/db.py` | 已经使用 `PRAGMA user_version` 和追加式 `MIGRATIONS`，这是正确基线，不能改成重建数据库。 |
| 模块清单读取 | `app/module_registry.py` | 能读取磁盘上的 `module.json`，但还没有“一个项目的完整执行计划”。 |
| 子进程/网页执行 | `app/module_runner.py` | 当前每个项目只允许一个模块；运行记录是单个模块粒度，不能表达整条项目流程。 |
| APEX 启动模块 | `modules/apex-launcher/` | 已能真实启动、关闭、重启；不能因为重构而退回假成功或临时 service。 |

网页模块是“一次性请求系统浏览器打开网址”，不是可由总控台终止的后台进程。因此它将被明确标成“已触发”，不能在界面上被假装成“正在运行”。

## 目标架构：每层只做一类事

图表：[后端完善路线图](D:/Projects/apex-console/backend/docs/backend-development-plan.html)。可点击图中顶部的三个阅读视图：一次请求、运行项目、安全与可验证边界。

1. **接口层（routers + 请求模型）**：接收 `/api` 请求、校验格式、把统一的业务错误转换成 HTTP 响应。它不直接编排 SQL 或启动进程。
2. **业务服务层（services）**：实现“新建项目”“删除前预演”“保存基本资料”“提交执行”等用户意图；一个跨表操作只在这里协调。
3. **数据访问层（repositories）**：只负责 SQLite 的查询、写入和事务，不知道 FastAPI 或页面文案。
4. **执行引擎（execution service）**：把项目绑定的模块排成计划，按顺序运行，第一处失败立刻结束；关闭反序执行，重启严格按“完整关闭 → 完整启动”。
5. **模块注册表和模块运行器**：继续负责“这个模块有哪些动作”和“如何实际运行一个动作”。它们不负责决定整个项目的业务流程。
6. **验证护栏**：迁移升级测试、接口契约测试、模拟模块故障测试与最少量人工 APEX 实测。每一步通过后才做下一步。

## 分阶段计划

### 阶段 0：锁定基线，不改变用户看到的行为

**目的**：先确保重构有可回退的事实依据。

- 为现有 `/api/bootstrap`、项目/任务/记录/模块/运行接口补齐“特征测试”：输入、成功响应、失败响应和重启后的数据状态。
- 把现有迁移 v1–v6 的升级路径逐个保留测试；数据库版本高于程序时继续拒绝启动。
- 记录当前 `run`、`stop`、`restart` 的真实行为，特别是 APEX 模块与网页模块的区别。
- 不新增数据表、不改前端接口、不动 APEX 的真实启动逻辑。

**验收**：前端 `node smoke-test.js` 输出 `ALL_PASS`；后端测试在项目可写的临时目录中全部通过；已有数据库原地打开后数据不丢失。

### 阶段 1：整理职责，但保持接口兼容

**目的**：让后续功能加在稳定边界上，而不是继续把 `main.py` 变大。

建议新增的目录（名称可按实际代码微调）：

```text
backend/app/
  routers/          # HTTP 路由：projects, tasks, notes, modules, runs
  services/         # 用户意图和业务规则
  repositories/     # SQLite 查询、写入和事务
  schemas/          # FastAPI 请求/响应模型
  execution/        # 后续项目执行计划的专属逻辑
```

- 先从“项目、任务、记录”这一条已稳定的垂直链路拆分：路由调用 service，service 调用 repository。
- `/api/...` 路径、JSON 字段、错误含义先保持不变，前端无需同步大改。
- 所有删除仍由 service 先计算预演结果，再执行删除；项目文件只移除登记，不删除磁盘文件。
- 统一业务错误类型，例如“找不到”“冲突”“不允许的状态”“执行前置条件不满足”；接口层集中映射为 404、409、422。

**验收**：阶段 0 的特征测试无需改写即可通过；同一条业务规则不再分别散落在多个路由里；无 schema migration。

### 阶段 2：引入项目执行计划（已完成）

**目的**：替换“每个项目只允许一个模块”的临时限制，但不牺牲真实失败语义。

1. 允许一个项目绑定多个模块，使用已有 `project_modules.sort_order` 排序。
2. 新增一个“项目执行”总记录；其下有多条“执行步骤”记录。原有 `runs` 继续保存每个模块动作的原始日志、退出码和结果。
3. 点击运行时先做完整预检：项目存在、至少一个已启用模块、每一步支持所需动作、项目/工作目录存在、没有同一项目的活动执行。
4. 预检通过后创建执行总记录，再依次调用现有模块运行能力；前一模块未成功，后一模块绝不启动。
5. `stop` 从最后一个可停止模块向前执行；`restart` 必须等待完整 stop 成功后才创建 run 阶段。任何一步失败均停止并保留原始错误。
6. 服务启动时把数据库中仍是 queued/running 的执行标记为 `interrupted`（中断），而不是猜测 Windows 子进程还在。这是诚实的失败状态，用户可重新运行或先人工确认。

建议追加迁移 v7（只追加，绝不重写旧迁移）：

| 新表 | 保存的内容 | 为什么需要 |
| --- | --- | --- |
| `project_executions` | 项目、动作、整体状态、开始/结束时间、失败摘要 | 一次“运行项目”是一个整体，不等同于某一个模块。 |
| `execution_steps` | 所属执行、排序、模块与动作快照、状态、关联 `run_id`、错误 | 能恢复“第几步发生了什么”，即使之后模块配置被修改。 |

推荐状态：`queued → running → succeeded / failed / stopped / interrupted`。状态只能向前推进；数据库事务负责创建计划，异步运行器负责更新实际结果。

**接口演进方式**：先新增 `/api/projects/{id}/executions` 与 `/api/executions/{id}`；旧的 `/run`、`/stop`、`/restart` 暂时代理到新执行引擎，待前端改为读取新返回结构后再安排弃用窗口。这样不会一次打断既有界面。

**验收**：用三个模拟模块验证顺序成功、第二步失败即停止、关闭反序、重启先关后开、服务重启标记中断、删除运行中项目被拒绝；再只做一轮管理员权限下的 APEX 实测。单轮实测只能证明当次成功，不能宣称长期稳定。

**本次结果**：数据库迁移、顺序运行、第二步失败即停、重启“停止后运行”以及服务重启标记中断均已由后端自动测试覆盖。真实 APEX 管理员环境尚未在本阶段执行；它应作为下一次人工验证单独记录，不能用模拟测试替代。

### 阶段 3：让页面能准确展示执行事实（已完成）

**目的**：让用户不必猜后台在做什么。

- `/api/bootstrap` 增加“最近项目执行摘要”，避免靠前端拼接假历史。
- 增加查询单次项目执行详情的接口：总状态、每一步状态、每步日志、失败原因。
- 先沿用轮询，不急着引入 WebSocket 或 SSE；只有确认轮询无法满足体验时才单独评估实时推送。
- 前端的流程节点完全依据服务端步骤状态渲染；关闭动作不计入“运行次数”。

**验收**：刷新页面后，历史、运行次数、正在执行的步骤和失败原因仍与后端一致；后端不可达时前端不显示假成功。

**本次结果**：`/api/bootstrap` 现返回每个项目的最新与活动执行摘要；页面改为创建并轮询项目执行接口，直接映射后端步骤状态与每步原始日志。自动测试覆盖启动数据详情与页面恢复逻辑；未使用 WebSocket 或 SSE。

### 阶段 4：稳固与收口（自动回归已完成）

**目的**：让新增能力可长期维护。

- 为所有新增迁移补“旧库升级”“新库创建”“未来版本拒绝启动”测试。
- 为执行引擎加入超时、重复提交、模块缺失、工作目录缺失、输出格式异常的回归测试。
- 将运行目录保留策略只做为独立议题；它不能顺带变成“版本/快照功能”。
- 写一份给模块作者的最小 `module.json` 约定：动作声明、超时、是否可停止、受控进程与一次性动作的区别。

**验收**：测试覆盖每种失败状态；删除模块与删除项目仍符合预演和历史保留规则；无新增死代码或假数据。

**本次结果**：自动测试已覆盖超时、重复提交、模块定义缺失、工作目录缺失、无效结果格式与运行中删除保护；所有后端回归通过。2026-09-20 已在真实 APEX 管理员环境完成一轮启动、关闭、重启：执行记录 `0b6cdf7a`、`d651e396`、`45b6ff30` 均成功，重启步骤顺序为 `stop → run`。最后一次重启后项目处于运行状态；这是一轮实测记录，不代表长期稳定性保证。

## 开始实施时的第一张小任务单

建议先只做 **阶段 0 + 阶段 1 中项目/任务/记录的路由拆分**，不要同时做多模块执行。

- 改动范围限定在 `backend/app/` 与 `backend/tests/`。
- 不新增数据库迁移，不改 `app.js`，不动 `modules/apex-launcher/runner.py`。
- 完成后先跑后端回归与前端冒烟；通过后再评审代码结构。
- 阶段 2 已完成 schema v7 和项目执行引擎；阶段 3 才开始消费这份执行详情来更新页面。

这是最小、可独立验收的一步：它先降低后续改动风险，但不会假装已经具备多模块执行能力。

## 设计前的关键问题与当前答案

| 问题 | 当前决定 |
| --- | --- |
| 是否把执行状态只放内存？ | 否。内存只管理当前 async task；执行事实与最终结果必须写 SQLite。 |
| 服务重启时能否继续宣称项目运行中？ | 否。除非以后增加可靠的进程归属验证；本轮统一标记为中断。 |
| 网页模块是否支持关闭？ | 否。它只请求系统打开网址，不拥有浏览器进程。 |
| 是否一次重写所有接口？ | 否。以兼容的 service 抽离和新执行端点逐步迁移。 |
| 是否顺便做版本/快照数据？ | 否。该主题单独评审，避免扩大 migration 风险。 |
| 是否先上实时推送、队列或云服务？ | 否。先用 SQLite、顺序执行、轮询和明确状态把本机流程做扎实。 |

## 实施纪律

- 新迁移只能追加到 `MIGRATIONS`，并由 `PRAGMA user_version` 驱动；旧数据必须保留，未来版本必须失败关闭。
- 真实执行、文件打开、删除、UAC 都不能以“看起来成功”的方式降级。
- 每阶段先测试模拟模块，再做最少量真实 APEX 验证；真实环境结果和自动测试结果分别报告。
- Windows 上 pytest 使用项目内可写的 `--basetemp`，避免系统临时目录权限错误被误判为代码失败。
